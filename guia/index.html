Capítulo 00

Las tres piezas, y qué hace cada una

Antes de escribir una sola línea de configuración: este stack son tres programas separados que se pasan datos por HTTP. Confundir cuál hace qué es la causa de la mitad de los problemas que vas a tener.

Promtail
El agente. Vive donde están los archivos de log. Los lee línea a línea, les saca metadatos, y los envía a Loki por HTTP. No almacena nada. Es el equivalente a Filebeat o Fluent Bit.
Loki
La base de datos. Recibe las líneas, las comprime en bloques y las guarda. Responde consultas en un lenguaje propio, LogQL. No tiene interfaz gráfica: solo una API HTTP.
Grafana
La cara visible. No guarda tus logs. Le hace preguntas a Loki y dibuja las respuestas. Si Grafana no ve datos, el problema casi nunca está en Grafana.
La idea que hay que entender

Loki no indexa el texto de tus logs. Elasticsearch construye un índice invertido de cada palabra, y por eso es caro. Loki solo indexa un puñado de etiquetas (labels) y guarda el resto del texto comprimido en bloques opacos. Buscar dentro del texto es una lectura secuencial forzada.

Todo lo demás de esta guía —por qué las etiquetas importan tanto, por qué hay límites de cardinalidad, por qué una query mal escrita tarda diez minutos— sale de esa única decisión de diseño.

Capítulo 01

Levantar el stack desde un directorio vacío

Lo único que necesitas instalado es Docker con el plugin Compose. Comprueba que lo tienes:

Todo el proyecto son cinco archivos. Esta es la estructura final, para que sepas hacia dónde vas:

árbolestructura del proyecto
grafana-loki-demo/
├── docker-compose.yml           # orquesta los 3 servicios
├── loki-config.yml              # cómo almacena y valida Loki
├── promtail-config.yml          # qué archivos leer y cómo parsearlos
├── logs/
│   └── access.log               # los logs que quieres ingerir
└── grafana/

docker-compose.yml, línea por línea

docker-compose.ymlservicio loki
services:
  loki:
    image: grafana/loki:2.9.0
    ports:
      - "3100:3100"
    volumes:
      - ./loki-config.yml:/etc/loki/local-config.yaml
      - loki-data:/tmp/loki
    command: -config.file=/etc/loki/local-config.yaml
    healthcheck:
      test: ["CMD-SHELL", "wget -q -O- http://localhost:3100/ready | grep -q ready || exit 1"]
      interval: 10s
      retries: 30
      start_period: 30s
image
Fija la versión. :latest te romperá el proyecto un martes cualquiera cuando cambie el formato de configuración entre versiones mayores.
ports
"3100:3100" expone el puerto del contenedor en tu máquina. Solo lo necesitas para hacer curl desde el host: Grafana habla con Loki por la red interna, no por aquí.
volumes
El primero es un bind mount: coloca tu archivo de configuración dentro del contenedor. El segundo es un volumen con nombre: hace que los datos sobrevivan a un docker compose down.
command
Sobrescribe el arranque por defecto de la imagen para apuntar a tu configuración. Si la ruta no coincide con la del volumen, Loki arranca con valores por defecto y no te avisa de forma obvia.
healthcheck
Sondea /ready. Sin esto no puedes usar condition: service_healthy, y Promtail arrancará antes que Loki para estrellarse contra un puerto cerrado.

  promtail:

Trampa · permisos de volumen

Loki corre dentro del contenedor como el usuario 10001, pero Docker crea los volúmenes nuevos como root. La primera vez verás mkdir /tmp/loki/rules: permission denied y el contenedor morirá en bucle. Se arregla una sola vez:

docker run --rm -v tuproyecto_loki-data:/data alpine:3 \
  sh -c 'mkdir -p /data/chunks /data/rules /data/wal && chown -R 10001:10001 /data'

En producción esto no se parece

El docker-compose.yml de arriba está pensado para tu máquina. Lo que cambia al salir de ella:

En local este proyecto
  • La contraseña va escrita en el compose: admin.
  • El puerto 3100 se publica al host para poder hacer curl.
  • Los archivos de configuración se montan desde el repositorio.
  • Si un contenedor muere, se queda muerto.
local
  ports:
    - "3100:3100"
  environment:
    - GF_SECURITY_ADMIN_PASSWORD=admin
  volumes:
    - ./loki-config.yml:/etc/loki/local-config.yaml
En producción qué cambia
  • La contraseña sale de un secreto, nunca del archivo versionado.
  • Loki no se publica al exterior. Solo Grafana lo alcanza por la red interna.
  • La configuración llega como ConfigMap o secreto del orquestador.
  • restart y límites de recursos, para que un pico de logs no se coma el host.
producción
  # sin 'ports': queda solo en la red interna
  expose:
    - "3100"
  environment:
    - GF_SECURITY_ADMIN_PASSWORD__FILE=/run/secrets/gf_admin
  secrets:
    - gf_admin
  restart: unless-stopped
  deploy:
    resources:
      limits: { memory: 2G }
El error de seguridad más repetido

Publicar el puerto 3100 de Loki en una máquina con IP pública. Loki no tiene autenticación propia: auth_enabled no es un login, solo decide si exige la cabecera de inquilino. Quien alcance ese puerto puede leer todos tus logs y escribir los que quiera. Loki va detrás de un proxy con TLS y autenticación, o no sale de la red interna.

Conectar Grafana con Loki sin tocar la interfaz

Puedes añadir el origen de datos a mano desde el navegador, pero se pierde al recrear el contenedor. El provisioning lo declara en un archivo:

grafana/provisioning/datasources/loki.yml
apiVersion: 1
datasources:
  - name: Loki
    type: loki
    access: proxy
    uid: loki                      # fíjalo tú; si no, Grafana genera uno aleatorio
    url: http://loki:3100          # nombre del servicio, NUNCA localhost
    isDefault: true
    jsonData:
      maxLines: 5000
      timeout: 300
access: proxy
El navegador pide a Grafana y Grafana pide a Loki. Con direct sería tu navegador quien llamara a Loki, y desde ahí el nombre loki no existe.
uid
El identificador que usan los paneles para referirse a este origen. Si dejas que Grafana lo invente, tus dashboards apuntarán a un uid muerto en cuanto recrees el volumen.
url
El error número uno de todo el proyecto. localhost dentro del contenedor de Grafana es el propio Grafana, no Loki.

Los archivos que no son obvios

Hay varios archivos en el proyecto que aparecen mencionados pero sin explicar bien qué son, cómo se ven en local y cómo cambian en producción.

En local five archivos
  • docker-compose.yml → orquesta los tres contenedores y sus volúmenes.
  • loki-config.yml → cómo Loki almacena, valida y compacta.
  • promtail-config.yml → qué archivos leer y cómo parsearlos.
  • .gitignore → excluye logs/ (425 MB) y promtail-data/.
  • vercel.json → publica solo la guía en Vercel, no el stack.
En producción estructura distinta
  • Kubernetes manifests en vez de compose.
  • ConfigMap por archivo de configuración.
  • .gitignore idéntico.
  • Helm values para los secretos.
  • CI/CD que genera los dashboards con código.

grafana/provisioning/datasources/loki.yml

Grafana ejecuta todo lo que hay en /etc/grafana/provisioning al arrancar, sin que toques la interfaz. El datasource declara cómo conectar con Loki:

Grafana corre en Docker y loki es el nombre en la red interna de compose.

En producción endpoint remoto con TLS

Capítulo 02

loki-config.yml, término por término

Loki es un sistema distribuido metido dentro de un solo binario. Los nombres de la configuración vienen de sus componentes internos, así que primero conviene ver por dónde pasa una línea de log.

El esqueleto mínimo

loki-config.ymlbloques base
auth_enabled: false

server:
  http_listen_port: 3100
  grpc_listen_port: 9096

common:
  path_prefix: /tmp/loki
  storage:
    filesystem:
      chunks_directory: /tmp/loki/chunks
      rules_directory: /tmp/loki/rules
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory

schema_config:
  configs:
    - from: 2020-01-01
      store: tsdb
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h
auth_enabled
Con false, Loki coloca todo en un inquilino ficticio llamado fake. Con true, cada petición debe traer la cabecera X-Scope-OrgID o falla. Para una demo local siempre false.
replication_factor
Cuántas copias de cada línea se guardan en el anillo. En un solo nodo tiene que ser 1; cualquier otro valor deja a Loki esperando réplicas que no existen.
ring / kvstore
El anillo es cómo se reparten el trabajo varios Lokis. Con inmemory le dices “soy el único, no busques compañeros”. En producción real esto sería Consul o etcd.
schema_config
El formato del índice. tsdb + v13 es el moderno y el que debes usar. El campo from es una fecha de inicio de vigencia: para cambiar de esquema se añade una entrada nueva con fecha futura, nunca se edita la existente.
period: 24h
El índice se parte en tablas de un día. No lo toques.

El mismo archivo, en un cluster real

Los tres bloques de arriba —common, ring y schema_config— son justo los que cambian al pasar de una máquina a varias. Esta comparación es la diferencia entre una demo y algo que aguanta.

En local un solo proceso

Todo en disco, sin coordinación con nadie: no hay más nodos con los que hablar.

local
common:
  path_prefix: /tmp/loki
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory
  storage:
    filesystem:
      chunks_directory: /tmp/loki/chunks

schema_config:
  configs:
    - object_store: filesystem
En producción varios nodos

Los chunks van a almacenamiento de objetos —cualquier nodo debe poder leerlos— y los nodos se descubren entre sí por memberlist.

producción
common:
  path_prefix: /loki
  replication_factor: 3
  ring:
    kvstore:
      store: memberlist
  storage:
    s3:
      endpoint: s3.us-east-2.amazonaws.com
      region: us-east-2
      bucketnames: loki-chunks-prod
      access_key_id: ${S3_ACCESS_KEY_ID}
      secret_access_key: ${S3_SECRET_ACCESS_KEY}

memberlist:
  join_members:
    - loki-memberlist:7946

schema_config:
  configs:
    - object_store: s3
object store
S3, GCS, Azure Blob o MinIO si te lo montas tú. La razón no es el tamaño: es que cualquier nodo tiene que poder leer los chunks que escribió otro. Con filesystem cada nodo solo ve los suyos.
memberlist
Un protocolo de cotilleo por el que los nodos se descubren solos. Sustituye al inmemory de un solo proceso sin necesidad de montar Consul.
replication_factor: 3
Cada línea se guarda en tres ingesters. Si uno cae, no pierdes nada. Exige al menos tres nodos: ponerlo con menos deja a Loki esperando réplicas que no llegan.
${VARIABLES}
Loki no expande variables de entorno por defecto. Hay que arrancarlo con -config.expand-env=true o el literal ${S3_ACCESS_KEY_ID} viajará tal cual como clave.

Retención: en local no existe, en producción es obligatoria

Este stack no borra nada nunca. En producción eso llena el bucket y encarece la factura mes a mes.

En local sin retención

No hay compactor y retention_period vale 0: los datos se quedan hasta que borres el volumen a mano.

Para una demo está bien. Es, de hecho, lo que hace este proyecto.

En producción compactor

El compactor es quien aplica la retención y compacta índices. Sin él, retention_period se ignora en silencio.

producción
compactor:
  working_directory: /loki/compactor
  retention_enabled: true
  delete_request_store: s3

limits_config:
  retention_period: 744h   # 31 días

limits_config — los límites que te van a frenar

Este bloque es donde vive casi todo lo que hace que Loki rechace tus datos. Los valores por defecto están pensados para logs que llegan en tiempo real, no para cargar un histórico.

loki-config.ymllimits_config
limits_config:
  reject_old_samples: false
  reject_old_samples_max_age: 8760h
  creation_grace_period: 8760h
  unordered_writes: true

  ingestion_rate_mb: 512
  ingestion_burst_size_mb: 1024
  per_stream_rate_limit: 512MB
  per_stream_rate_limit_burst: 1024MB

  max_query_length: 0
  max_query_lookback: 0
  max_entries_limit_per_query: 10000
  split_queries_by_interval: 24h
ParámetroPor defectoQué pasa si lo dejas así
reject_old_samplestrueRechaza cualquier línea más vieja que reject_old_samples_max_age. Ponlo a false para cargar históricos.
creation_grace_period10mMargen hacia el futuro. Si el reloj de tu contenedor va adelantado o tus logs tienen fechas futuras, se descartan en silencio.
unordered_writestruePermite líneas desordenadas dentro de una ventana. Es lo que habilita el control nº 2 del diagrama.
per_stream_rate_limit3MBEl límite que casi nadie ve venir. Es por stream, no global. Si todos tus logs caen en un stream, 3 MB/s es tu techo real por mucho que subas ingestion_rate_mb.
max_query_length721hUna consulta de más de 30 días falla. 0 lo desactiva.
max_entries_limit_per_query5000Techo de líneas devueltas por consulta de logs. No afecta a las métricas.
split_queries_by_interval30mTrocea una consulta larga en subconsultas paralelas. Con históricos largos, 24h va mejor.
En local límites abiertos

Aquí los límites estorban: quieres cargar de golpe un histórico de 30 días. Se abren de par en par a propósito.

local
reject_old_samples: false
ingestion_rate_mb: 512
per_stream_rate_limit: 512MB
max_query_length: 0       # sin tope
max_global_streams_per_user: 0
En producción límites como defensa

Aquí los límites te protegen: de una aplicación que entra en bucle, de una etiqueta con cardinalidad descontrolada, de una consulta que barre un año.

producción
reject_old_samples: true
reject_old_samples_max_age: 168h
ingestion_rate_mb: 10
per_stream_rate_limit: 5MB
max_global_streams_per_user: 10000
max_query_length: 721h
split_queries_by_interval: 30m
Los límites cambian de bando

Es el giro conceptual del capítulo. En una demo un límite es un obstáculo entre tú y tus datos; en producción es lo único que separa un incidente de una aplicación de una caída de toda tu observabilidad. max_global_streams_per_user no está en la configuración local de este proyecto —vale 0, sin tope— y en producción es probablemente el ajuste más importante de la lista.

ingester — memoria y ventana temporal

loki-config.ymlingester
ingester:
  max_chunk_age: 1560h       # tolerancia hacia atrás = la mitad de esto
  chunk_idle_period: 5m     # vuelca el chunk si el stream se calla
  chunk_target_size: 1572864 # ~1,5 MB: corta el chunk al llegar aquí
  chunk_encoding: snappy   # compresión rápida
Por qué van juntos

Subir max_chunk_age a 1560 horas suena a que los datos se quedarán en RAM dos meses. No ocurre, porque chunk_idle_period y chunk_target_size también cierran chunks: el primero cuando el stream deja de recibir, el segundo cuando el bloque alcanza su tamaño. max_chunk_age es solo el último recurso de los tres. Por eso puedes subirlo sin que la memoria se dispare.

terminalvalidar sin arrancar
docker run --rm -v "$PWD/loki-config.yml:/etc/loki/local-config.yaml" \
  grafana/loki:2.9.0 -config.file=/etc/loki/local-config.yaml -verify-config

Responde msg="config is valid" o te dice exactamente qué línea está mal. Úsalo antes de cada up.

Capítulo 03

promtail-config.yml y el pipeline de parseo

Promtail tiene tres responsabilidades: saber qué archivos leer, recordar por dónde iba, y decidir qué etiquetas lleva cada línea.

promtail-config.ymlestructura completa
server:
  http_listen_port: 9080
  grpc_listen_port: 0          # 0 = desactivado, no lo necesitas

positions:
  filename: /tmp/positions.yaml  # memoria de por dónde iba cada archivo

clients:
  - url: http://loki:3100/loki/api/v1/push
    batchwait: 1s              # espera antes de enviar un lote incompleto
    batchsize: 1048576         # 1 MB por lote
    backoff_config:
      min_period: 500ms
      max_period: 5s
      max_retries: 10

scrape_configs:
  - job_name: nginx-demo-logs
    static_configs:
      - targets: [localhost]
        labels:
          job: nginx_access          # etiqueta fija para todo el archivo
          __path__: /var/log/app-logs/access.log

    pipeline_stages:
      - regex:
          expression: '^(?P<ip>[^ ]+) - - \[(?P<timestamp>[^\]]+)\] "(?P<method>[A-Z]+) (?P<endpoint>[^ ]+) [^"]*" (?P<status>\d{3}) (?P<bytes>\d+)'
      - timestamp:
          source: timestamp
          format: "02/Jan/2006:15:04:05 -0700"
      - labels:
          status:

Las cuatro claves que importan

positions
Un YAML con el offset en bytes de cada archivo. Si Loki rechaza un lote, Promtail reintenta, se rinde y avanza igualmente: esas líneas se pierden. Para reprocesar un archivo desde cero hay que borrar este archivo y reiniciar.
__path__
Los guiones bajos dobles marcan una etiqueta interna: se usa y se descarta, no llega a Loki. Acepta comodines, pero evítalos si tienes archivos con formatos distintos: un *.log se traga todo y le aplica el parseo equivocado.
stage regex
Extrae campos con nombre. Sintaxis Go: (?P<nombre>…). Lo extraído vive solo durante el pipeline; no se convierte en etiqueta por sí solo.
stage timestamp
Le dice a Loki que use la fecha de dentro del log, no la hora de lectura. Sin esta etapa, un log de julio se guarda con la marca de hoy.
stage labels
Promociona un campo extraído a etiqueta indexada. Aquí es donde se hace daño. Ver capítulo siguiente.

De rutas fijas a descubrimiento automático

El static_configs de arriba nombra los archivos uno a uno. Eso solo funciona mientras sepas de antemano qué hay en la máquina; en cuanto los contenedores se crean y destruyen solos, deja de servir.

En local rutas escritas a mano

Sabes exactamente qué archivo quieres y dónde está. Las posiciones viven en un directorio del proyecto.

local
positions:
  filename: /tmp/positions.yaml

clients:
  - url: http://loki:3100/loki/api/v1/push

scrape_configs:
  - job_name: nginx-demo-logs
    static_configs:
      - targets: [localhost]
        labels:
          __path__: /var/log/app-logs/access.log
En producción service discovery

Promtail pregunta al orquestador qué hay corriendo y se entera solo de los pods nuevos. Las etiquetas se derivan del propio cluster.

producción
positions:
  filename: /var/lib/promtail/positions.yaml

clients:
  - url: https://loki.midominio.com/loki/api/v1/push
    tenant_id: tienda
    basic_auth:
      username: promtail
      password_file: /etc/promtail/secrets/loki-password
    tls_config:
      ca_file: /etc/ssl/certs/ca-certificates.crt

scrape_configs:
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: app
      - action: drop
        source_labels: [__meta_kubernetes_pod_phase]
        regex: (Succeeded|Failed)
positions
En local está en /tmp y no pasa nada si se pierde. En producción tiene que ir en un volumen persistente: si el pod reinicia y las posiciones se fueron, Promtail relee cada archivo desde el principio y duplicas todos los logs.
tenant_id
Obligatorio si activaste auth_enabled: true. En local no existe porque solo hay un inquilino ficticio.
password_file
Un archivo, no la contraseña en línea. Así el secreto lo monta el orquestador y nunca aparece en la configuración.
action: drop
Descarta targets antes de leerlos. Sin esta regla acabas ingiriendo los logs de todos los pods terminados del cluster.
El formato de fecha de Go

Go no usa %Y-%m-%d. Usa una fecha de referencia concreta —lunes 2 de enero de 2006 a las 15:04:05 con huso −0700— y tú escribes esa misma fecha con la forma que tenga tu log. Por eso 27/Jul/2026:07:00:26 +0000 se declara como 02/Jan/2006:15:04:05 -0700. Los números no son arbitrarios: son 1, 2, 3, 4, 5, 6, 7 en orden.

Capítulo 04

Labels, streams y por qué la cardinalidad te arruina el día

Este es el concepto central de Loki. Si solo te llevas una cosa de la guía, que sea esta.

Un stream es el conjunto de líneas que comparten exactamente la misma combinación de etiquetas. Loki no guarda “logs”: guarda streams, y cada stream tiene sus propios bloques, su propio índice y su propio límite de velocidad.

Qué sí y qué no

Campo¿Etiqueta?Motivo
jobSíUn puñado de valores, definidos por ti.
statusSíLos códigos HTTP son un conjunto cerrado y pequeño.
endpointSí, con cuidadoBien si son rutas fijas. No si llevan identificadores: /users/8412 es cardinalidad infinita disfrazada.
ipNoMiles de valores. Extráela al consultar.
request_timeNuncaUn valor decimal distinto por línea.
trace_idNuncaÚnico por definición. Este es el caso de libro.

El presupuesto real de streams

En local da lo mismo

Con 20 streams y un solo proceso, la cardinalidad es un concepto teórico. Puedes equivocarte y no notarlo.

Por eso este proyecto tiene max_global_streams_per_user: 0 — sin tope.

En producción se paga en RAM

Cada stream activo mantiene un chunk abierto en memoria de cada ingester, multiplicado por el factor de replicación.

Una etiqueta mal elegida en un despliegue puede tirar los ingesters en minutos. Por eso se pone un tope y se vigila.

producción
limits_config:
  max_global_streams_per_user: 10000
  max_label_names_per_series: 15
Cómo vigilarlo antes de que duela

Loki publica en /metrics el número de streams activos. Un panel con loki_ingester_memory_streams y una alerta cuando se acerque a tu tope avisa antes de que el ingester se quede sin memoria. Es de los primeros paneles que conviene montar en un despliegue real.

La consecuencia práctica

Los campos que no son etiquetas no se pierden: siguen en el texto de la línea. Simplemente los extraes en el momento de consultar, con | pattern o | regexp. Cuesta más CPU al leer, pero no envenena el índice.

Capítulo 05

Varios proyectos y varias fuentes en el mismo Loki

La pregunta llega en cuanto el stack funciona: tengo cinco proyectos, ¿levanto cinco Lokis? No. Un solo Loki aloja todos, y lo que los separa son las etiquetas. Pero hay tres formas de organizarlo y elegir mal sale caro.

A · Un bloque de scrape por proyecto

Lo más directo, y lo correcto cuando cada proyecto escribe un formato distinto. Cada bloque tiene su propio __path__ y su propio pipeline.

promtail-config.ymlun bloque por proyecto
scrape_configs:
  - job_name: tienda
    static_configs:
      - targets: [localhost]
        labels:
          project: tienda
          env: prod
          __path__: /var/log/tienda/*.log
    pipeline_stages:
      - regex: { expression: '…formato de nginx…' }
      - labels: { status: }

  - job_name: api-pagos
    static_configs:
      - targets: [localhost]
        labels:
          project: api-pagos
          env: prod
          __path__: /var/log/pagos/*.log
    pipeline_stages:
      - json:                        # este proyecto escribe JSON
          expressions: { level: level, msg: message }
      - labels: { level: }
Monta los directorios en el compose

Promtail solo ve lo que le montes. Cada proyecto necesita su bind mount:

  promtail:
    volumes:
      - ./proyectos/tienda/logs:/var/log/tienda:ro
      - ./proyectos/pagos/logs:/var/log/pagos:ro
      - ./promtail-config.yml:/etc/promtail/config.yml

El :ro es deliberado: Promtail no tiene por qué escribir en los logs de nadie.

B · Un glob y el nombre del proyecto sacado de la ruta

Cuando todos los proyectos comparten estructura, no hace falta un bloque por cada uno. Se recorre con un comodín y se deduce la etiqueta de la propia ruta del archivo.

La clave es que Promtail añade automáticamente una etiqueta filename con la ruta completa de cada archivo. El stage regex puede leerla con source en vez de leer el contenido de la línea.

promtail-config.ymlrelabeling desde la ruta
scrape_configs:
  - job_name: proyectos
    static_configs:
      - targets: [localhost]
        labels:
          job: proyectos
          __path__: /var/log/proyectos/*/*.log
    pipeline_stages:
      # `source: filename` lee la RUTA, no el contenido de la línea
      - regex:
          source: filename
          expression: '/var/log/proyectos/(?P<project>[^/]+)/(?P<logfile>[^/]+)\.log$'
      - regex:
          expression: '^(?P<ip>[^ ]+) - - \[(?P<timestamp>[^\]]+)\] "(?P<method>[A-Z]+) (?P<endpoint>[^ ]+) [^"]*" (?P<status>\d{3})'
      - timestamp: { source: timestamp, format: "02/Jan/2006:15:04:05 -0700" }
      - labels:
          project:
          logfile:
          status:

Con esta estructura de directorios:

árboluna carpeta por proyecto
logs/proyectos/
├── tienda/
│   ├── access.log
│   └── error.log
└── api-pagos/
    └── access.log

salen exactamente estos streams —comprobado sobre un Loki real:

projectlogfilestatuslíneas
api-pagosaccess2013
tiendaaccess2003
tiendaerror5003

Y a partir de ahí las consultas se vuelven naturales:

logqlconsultar por proyecto
{job="proyectos", project="tienda"}                    # todo un proyecto
{job="proyectos", project="tienda", logfile="error"}   # solo su log de errores
{job="proyectos", project=~"tienda|api-pagos"}         # varios a la vez

# comparar la tasa de error entre TODOS los proyectos
sum by (project) (rate({job="proyectos", status=~"5.."}[5m]))
Esa última consulta es el motivo de todo esto

Cruzar proyectos en una sola gráfica solo es posible si comparten inquilino y tienen una etiqueta común que los distinga. Es exactamente lo que la opción C te quita.

Descubrir contenedores de Docker automáticamente

Si tus proyectos son contenedores, no hace falta montar directorios: Promtail puede preguntarle al demonio de Docker qué hay corriendo y etiquetar cada log con el servicio al que pertenece.

promtail-config.ymldocker_sd_configs
scrape_configs:
  - job_name: contenedores
    docker_sd_configs:
      - host: unix:///var/run/docker.sock
        refresh_interval: 10s
    relabel_configs:
      # el nombre del contenedor llega como "/nombre": se le quita la barra
      - source_labels: ['__meta_docker_container_name']
        regex: '/(.*)'
        target_label: 'container'
      - source_labels: ['__meta_docker_container_label_com_docker_compose_service']
        target_label: 'servicio'
      - source_labels: ['__meta_docker_container_label_com_docker_compose_project']
        target_label: 'proyecto'

Compose escribe etiquetas en cada contenedor que crea, y de ahí salen servicio y proyecto sin que tengas que declararlos. Hay que montarle el socket:

docker-compose.yml
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
Necesitas Promtail 3.x

Promtail 2.9 habla la versión 1.42 de la API de Docker. Los demonios de Docker recientes exigen 1.44 como mínimo y responden:

client version 1.42 is too old. Minimum supported API version is 1.44

Con grafana/promtail:3.2.1 o superior funciona sin tocar nada más. Si necesitas quedarte en 2.9, la alternativa es leer los archivos directamente —/var/lib/docker/containers/*/*-json.log— y sacar el identificador del contenedor de la ruta, como en la opción B.

Otras fuentes que no son archivos

syslog
Promtail escucha en un puerto y recibe syslog por red: syslog: { listen_address: 0.0.0.0:1514 }. Útil para equipos de red y máquinas donde no puedes instalar nada.
journal
journal: { path: /var/log/journal } lee el diario de systemd. Requiere montar el directorio y suele necesitar max_age para no releer meses de histórico al arrancar.
kubernetes_sd
El equivalente a docker_sd para clústeres: descubre pods y trae namespace, pod y contenedor como etiquetas. Es el modo estándar en Kubernetes.
Push directo
Cualquier aplicación puede escribir a /loki/api/v1/push sin Promtail de por medio. Útil para trabajos por lotes que no dejan archivo.

C · Inquilinos separados, cuando hace falta aislamiento de verdad

Las etiquetas separan datos, no permisos: cualquiera con acceso al datasource puede consultar todo. Si necesitas que el equipo de un proyecto no pueda leer los logs de otro, o cuotas independientes, hay que usar la multi-tenencia de Loki.

loki-config.ymlactivar inquilinos
auth_enabled: true   # ahora cada petición DEBE traer X-Scope-OrgID
promtail-config.ymlun cliente por inquilino
clients:
  - url: http://loki:3100/loki/api/v1/push
    tenant_id: tienda
grafana/provisioning/datasources/loki.ymlun datasource por inquilino
datasources:
  - name: Loki — tienda
    type: loki
    uid: loki-tienda
    url: http://loki:3100
    jsonData:
      httpHeaderName1: 'X-Scope-OrgID'
    secureJsonData:
      httpHeaderValue1: 'tienda'

  - name: Loki — pagos
    type: loki
    uid: loki-pagos
    url: http://loki:3100
    jsonData:
      httpHeaderName1: 'X-Scope-OrgID'
    secureJsonData:
      httpHeaderValue1: 'pagos'

El aislamiento se completa con los permisos de Grafana: cada datasource se restringe a un equipo, y los paneles de un proyecto solo pueden apuntar al suyo.

Lo que pierdes

Una consulta no puede cruzar inquilinos. Ese sum by (project) (rate(…)) que compara la tasa de error de todos tus proyectos en una gráfica deja de ser posible. No actives la multi-tenencia porque suene más profesional: actívala cuando el aislamiento sea un requisito real.

Organizarlo en Grafana

Con las etiquetas puestas, un solo dashboard sirve para todos los proyectos. Se declara una variable y se usa en los selectores.

dashboard.jsonvariable de proyecto
"templating": { "list": [
  {
    "name": "project",
    "label": "Proyecto",
    "type": "query",
    "datasource": { "type": "loki", "uid": "loki" },
    "query": { "label": "project", "stream": "{job=\"proyectos\"}", "type": 1 },
    "refresh": 1,
    "includeAll": true,
    "multi": true
  }
]}

El campo stream limita los valores ofrecidos a los que existen dentro de ese selector, en vez de listar todos los valores de la etiqueta en todo Loki. Después, en cada panel:

logqlpanel reutilizable
sum by (project) (rate({job="proyectos", project=~"$project"}[$__interval]))
Carpetas
El folder del proveedor de dashboards agrupa por equipo. Puedes declarar varios proveedores apuntando a subdirectorios distintos, cada uno con su carpeta.
Un dashboard, no diez
Con la variable $project, un único dashboard cubre todos los proyectos. Diez copias del mismo JSON son diez sitios donde arreglar el mismo fallo.
Enlaces
Los data links de un panel pueden llevar al dashboard de detalle del proyecto seleccionado, pasando var-project=${__field.labels.project}.

El presupuesto de cardinalidad se multiplica

Recuerda el capítulo anterior: el número de streams es el producto de todas las etiquetas. Añadir project multiplica lo que ya tenías.

EtiquetasValoresStreams
job, status1 × 44
+ endpoint1 × 4 × 520
+ project (10 proyectos)10 × 4 × 5200
+ env (prod, staging, dev)10 × 4 × 5 × 3600

600 streams siguen siendo perfectamente manejables —Loki aguanta decenas de miles—, pero la progresión enseña la lección: cada etiqueta nueva multiplica, no suma. Antes de añadir una, pregúntate si de verdad vas a filtrar por ella.

Un orden que funciona

env primero, luego project, luego job o logfile, y por último el detalle del contenido (status, level). Los tres primeros los pones tú y son estables; el último sale del log y conviene vigilarlo.

Capítulo 06

LogQL desde cero

LogQL se lee de izquierda a derecha como una cinta transportadora: eliges un conjunto de líneas, las vas filtrando y transformando, y opcionalmente las conviertes en números.

Nivel 1 · Seleccionar streams

Lo mínimo que Loki acepta. Siempre entre llaves, siempre con al menos una etiqueta.

logqlselectores
{job="nginx_access"}                      # igual
{job="nginx_access", status="500"}        # dos etiquetas: es un Y lógico
{job=~"nginx.+"}                          # coincide con expresión regular
{job="nginx_access", status!="200"}       # distinto de
{status=~"4..|5.."}                       # regex: todos los 4xx y 5xx
Error de principiante

{job=~".+"} selecciona absolutamente todo y lee cada byte que tengas guardado. Loki no es Google: no hay una caja de búsqueda global. Empieza siempre por el selector más estrecho que puedas y ensánchalo si hace falta.

Nivel 2 · Filtrar el texto de la línea

OperadorSignificadoEjemplo
|=contiene{job="x"} |= "checkout"
!=no contiene{job="x"} != "healthz"
|~coincide con regex{job="x"} |~ "timeout|refused"
!~no coincide con regex{job="x"} !~ "^DEBUG"

Se encadenan, y el orden importa: pon primero el filtro que descarte más líneas, porque cada uno solo ve lo que le deja el anterior.

logqlencadenar filtros
{job="nginx_access"} |= "checkout" != "HTTP/1.0" |~ "50[0-9]"

Nivel 3 · Extraer campos con un parser

Hasta aquí la línea es una cadena opaca. Un parser la convierte en campos con nombre.

| pattern
El más legible para formatos de posición fija. Escribes la línea sustituyendo lo que quieres por <nombre> y lo que no te importa por <_>. Los literales entre medias deben coincidir exactamente.
| regexp
Para formatos irregulares. Sintaxis Go con grupos nombrados. Más potente y bastante más lento.
| json
Para logs en JSON. Sin argumentos convierte cada clave en un campo.
| logfmt
Para el formato clave=valor clave=valor.
logqlpattern sobre una línea de nginx
# la línea real:
# 192.168.1.7 - - [27/Jul/2026:07:00:26 +0000] "PUT /login HTTP/1.1" 200 887

{job="nginx_access"}
  | pattern `<ip> - - [<_>] "<method> <endpoint> <_>" <code> <bytes_sent>`
Cuidado con los nombres

No llames bytes ni duration a un campo que vayas a desenvolver. bytes() y duration() son funciones de conversión de LogQL, y | unwrap bytes resulta ambiguo. Usa bytes_sent, request_time y te ahorras un error que cuesta media hora encontrar.

Nivel 4 · Filtrar por campo extraído

Una vez parseada, la línea tiene campos con los que se puede comparar —incluso numéricamente.

logqlfiltros de campo
{job="nginx_timed"}
  | pattern `… <request_time> <_> <_>`
  | request_time > 2          # comparación numérica
  | endpoint = `/checkout`    # comparación de texto (comillas invertidas)

Nivel 5 · Reescribir la línea

line_format sustituye el texto por una plantilla Go. Sirve para dejar solo lo que te interesa mirar.

logqlline_format
{job="nginx_timed"}
  | pattern `<ip> - - [<_>] "<method> <path> <_>" <code> <_> "<_>" "<_>" <request_time> <_> <txn>`
  | request_time > 2
  | line_format `{{.request_time}}s [{{.code}}] {{.method}} {{.path}} {{.txn}}`

# resultado: 2.099s [500] PUT /login txn_a3f9c1b2

Nivel 6 · De logs a números

Aquí es donde una consulta se vuelve graficable. Hay dos familias y confundirlas es el error más común.

FamiliaSobre qué operaFunciones
Cuenta líneasEl número de líneas, sin mirar su contenido. No lleva unwrap.rate, count_over_time, bytes_rate, bytes_over_time
Mide valoresUn número extraído de cada línea. Exige unwrap.avg_over_time, sum_over_time, max_over_time, min_over_time, quantile_over_time, stddev_over_time
logqllas dos familias
# CUENTA: peticiones por segundo, por código de estado
sum by (status) (rate({job="nginx_access"}[5m]))

# MIDE: media de bytes por respuesta, por método
avg_over_time(
  {job="nginx_access"}
    | pattern `<_> - - [<_>] "<method> <_> <_>" <_> <bytes_sent>`
    | unwrap bytes_sent [5m]
) by (method)
Error real · count_over_time no admite unwrap

Si escribes count_over_time(… | unwrap x [5m]) Loki responde parse error: invalid aggregation count_over_time with unwrap. Cuenta líneas, no valores: quítale el unwrap.

Nivel 7 · La trampa del by()

Esta merece su propia sección porque produce gráficas que parecen correctas.

logqlp95 global de verdad
quantile_over_time(0.95,
  {job="nginx_timed"}
    | pattern `… <request_time> <_> <_>`
    | drop status, endpoint, filename
    | unwrap request_time [5m])

Nivel 8 · Media ponderada

Para un promedio global no basta con avg() por fuera: eso promedia promedios de tramos con distinto número de muestras. La forma correcta es dividir sumas.

logqlmedia ponderada
sum(sum_over_time({job="nginx_timed"} | pattern `…` | unwrap request_time [5m]))
/
sum(count_over_time({job="nginx_timed"}[5m]))

Con datos uniformes la diferencia es de décimas; con tráfico real desbalanceado, no.

La misma consulta cuesta muy distinto según dónde corra

En tu portátil una consulta lenta te hace esperar. En producción, con varias personas mirando dashboards a la vez, una consulta mal acotada satura a los queriers y tumba los paneles de todos.

En local sin red de seguridad

Todo desactivado para poder barrer 30 días sin que nada te corte.

Si una consulta tarda cinco minutos, es tu problema y el de nadie más.

local
max_query_length: 0
max_query_lookback: 0
split_queries_by_interval: 24h
En producción caché y troceado

Se trocea más fino para paralelizar, se cachean los resultados y se limita cuánto puede pedir una sola persona.

producción
limits_config:
  max_query_length: 721h
  max_query_parallelism: 32
  split_queries_by_interval: 30m

query_range:
  align_queries_with_step: true
  cache_results: true
  results_cache:
    cache:
      embedded_cache:
        enabled: true
        max_size_mb: 512
Las consultas caras se precalculan

Un quantile_over_time con unwrap sobre millones de líneas es carísimo, y en un dashboard se reejecuta con cada refresco. En producción eso se resuelve con el ruler: una regla de grabación calcula la métrica cada minuto y la guarda en Prometheus, y el panel consulta el resultado ya hecho en vez de recorrer los logs otra vez.

Variables de Grafana

En los paneles verás [$__interval] y [$__range]. El primero es el ancho de un píxel de la gráfica —Grafana lo calcula según el zoom—; el segundo es todo el rango de tiempo visible, y es el que se usa en las consultas instantáneas de los paneles Stat. $__auto hace lo mismo que $__interval pero solo existe desde Grafana 10.2.

Capítulo 07

El error que vas a ver: “entry too far behind”

Si cargas un histórico en Loki, este error aparece. Merece un capítulo entero porque la solución evidente —la que sugiere el propio mensaje— no funciona.

docker compose logs promtail
level=error caller=client.go:430 component=client host=loki:3100
  msg="final error sending batch" status=400
  error="entry with timestamp 2026-08-08 10:24:26 +0000 UTC ignored,
         reason: 'entry too far behind, oldest acceptable timestamp is:
         2026-08-25T20:58:33Z'"

Por qué reject_old_samples: false no lo arregla

Porque ese ajuste desactiva el control nº 1 del diagrama del capítulo 02, el del distributor. Este error viene del control nº 2, el del ingester, que es otro código y otro parámetro.

Con unordered_writes activo —lo está por defecto—, el ingester acepta líneas desordenadas solo dentro de una ventana hacia atrás igual a max_chunk_age / 2, medida desde la línea más reciente que ya vio ese stream. Con el valor por defecto de 2h, esa ventana es de una hora.

Las dos soluciones

De fondo
Ordena el archivo por fecha antes de ingerirlo. Si las líneas llegan en orden, cada una avanza la cabeza del stream y ninguna cae por detrás del corte. No hay nada que configurar.
De emergencia
Si no puedes ordenar el origen, ensancha la ventana. Recuerda que la tolerancia es la mitad de max_chunk_age: para cubrir 30 días de histórico necesitas al menos 1440 h, y conviene un margen.
loki-config.ymlsolución de emergencia
ingester:
  max_chunk_age: 1560h   # 1560/2 = 32,5 días de tolerancia hacia atrás

limits_config:
  reject_old_samples: false   # hace falta también, pero NO basta por sí solo
  reject_old_samples_max_age: 8760h
Después de arreglarlo, hay que rebobinar

Promtail reintenta un lote rechazado, se rinde y avanza la posición igualmente. Cambiar la configuración de Loki no recupera las líneas perdidas: hay que borrar el archivo de posiciones y reiniciar. Como lo escribe root dentro del contenedor, lo más cómodo es borrarlo desde otro contenedor:

docker compose down
docker run --rm -v "$PWD/promtail-data:/d" alpine:3 rm -f /d/positions.yaml
docker compose up -d

Este problema casi no existe en producción

Merece decirse, porque la solución de emergencia del apartado anterior es exactamente lo que no debes copiar a un entorno real.

En local cargas un histórico

Ingieres de golpe 30 días de logs generados y desordenados. Todo llega “viejo”, y por eso hay que abrir la ventana del ingester.

local
ingester:
  max_chunk_age: 1560h   # 65 días
limits_config:
  reject_old_samples: false
En producción los logs llegan al momento

Una aplicación viva escribe en orden y Promtail los envía en segundos. La ventana por defecto sobra, y dejarla estrecha es una protección: avisa de relojes desincronizados y de reprocesos accidentales.

producción
ingester:
  max_chunk_age: 2h       # el valor por defecto
limits_config:
  reject_old_samples: true
  reject_old_samples_max_age: 168h
Si ves este error en producción, no subas max_chunk_age

Ahí el error no es un obstáculo: es un síntoma. Casi siempre significa una de tres cosas: el reloj de una máquina va desfasado (revisa NTP), alguien reprocesó un archivo antiguo, o el stage timestamp está parseando mal la fecha y te la coloca en otro año. Ensanchar la ventana esconde el problema y llena tu almacenamiento de datos con fechas equivocadas.

Comprobar que funcionó

terminalverificación
# ¿queda algún rechazo?
docker compose logs promtail | grep -c "too far behind"

# ¿cuántas líneas ha aceptado Loki?
docker compose exec loki wget -qO- http://localhost:3100/metrics \
  | grep '^loki_distributor_lines_received_total'

# ¿existen ya las etiquetas?
curl -s http://localhost:3100/loki/api/v1/labels
Otra trampa de la misma familia

Un __path__ con comodín (*.log) se traga cualquier archivo nuevo del directorio y le aplica el parseo del primer trabajo que coincida. Si añades un archivo con otro formato, se ingiere con las etiquetas equivocadas y no te enteras hasta que una consulta devuelve nada. Usa rutas explícitas cuando convivan formatos distintos.

Capítulo 08

Medir latencia: lo que no está en el log no se puede consultar

El formato por defecto de nginx —common log format— no contiene ningún dato temporal por petición:

common log formatsin latencia
192.168.1.7 - - [27/Jul/2026:07:00:26 +0000] "PUT /login HTTP/1.1" 200 887
                                                                  ───┬─ ─┬─
                                                              status ──┘   │
                                                       body_bytes_sent ─┘

Ese último número son bytes, no milisegundos. Ninguna consulta puede extraer un dato que no se escribió. Hay que cambiar el log_format de nginx:

nginx.confformato con tiempos
log_format timed '$remote_addr - $remote_user [$time_local] "$request" '
                 '$status $body_bytes_sent "$http_referer" "$http_user_agent" '
                 '$request_time $upstream_response_time $request_id';

access_log /var/log/nginx/access.log timed;
$request_time
Lo que tarda desde el punto de vista del cliente: desde el primer byte de la petición hasta el último de la respuesta. Incluye red y TLS.
$upstream_response_time
Lo que tardó tu aplicación en responderle a nginx. Siempre menor.
La diferencia
Es el coste de red, TLS y buffering. Si se dispara, el problema no está en tu código. Graficar ambas superpuestas es de los paneles más útiles que puedes tener.
En local logs sintéticos

Un script de Python inventa las líneas y las escribe ya ordenadas, con un incidente colocado a propósito para tener algo que investigar.

El archivo nunca rota ni cambia de nombre.

En producción nginx de verdad

Las escribe nginx con el log_format que definas, y logrotate las rota cada noche. Promtail sigue la rotación solo si el patrón la contempla.

producción
# promtail: contempla el archivo rotado
__path__: /var/log/nginx/access.log

# logrotate: NO uses copytruncate,
# pierde líneas entre el copiado y el truncado
/var/log/nginx/*.log {
  daily
  rotate 14
  create 0640 www-data adm
  postrotate
    nginx -s reopen
  endscript
}
La rotación es donde se pierden logs

Con copytruncate, logrotate copia el archivo y luego lo vacía; lo que se escriba entre esas dos operaciones desaparece. Y si Promtail estaba leyendo por el descriptor antiguo, puede seguir apuntando a un archivo que ya nadie escribe. Usa create + postrotate con nginx -s reopen, que es lo que hace la configuración de arriba.

Media contra percentiles

La latencia no se distribuye como una campana: tiene una cola larga a la derecha. La media queda arrastrada por esa cola y aun así subestima lo que sufren los usuarios más desafortunados.

logqllas cuatro consultas de latencia
# media por endpoint — la gráfica base
avg_over_time({job="nginx_timed"}
  | pattern `<_> - - [<_>] "<_> <_> <_>" <_> <_> "<_>" "<_>" <request_time> <_> <_>`
  | unwrap request_time [$__interval]) by (endpoint)

Capítulo 09

Logs de un WAF: Cloudflare en tus dashboards

Hasta aquí los logs venían de archivos en tu disco. Un WAF es distinto: los logs los tiene un tercero, en su nube, y hay que ir a buscarlos. Cómo se hace depende de tu plan de Cloudflare, y esa es la primera decisión.

Qué es un WAF y qué escribe en sus logs

Un WAF (Web Application Firewall) se sienta delante de tu servidor e inspecciona cada petición antes de dejarla pasar. Cuando una coincide con una regla —una inyección SQL, un escaneo de rutas conocidas, un país bloqueado— la marca y actúa.

zone
En Cloudflare, un dominio. Cada zona tiene su propio identificador (zone_id) y sus propios logs. Si gestionas varios dominios, son varias zonas.
acción
Lo que el WAF decidió: allow, block, challenge (captcha), jschallenge, log (solo registra, no bloquea) o skip. Es el campo más importante de todos.
regla
Qué la disparó. Viene como identificador (WAFRuleID) y grupo de reglas. Una regla dispara mucho es señal de ataque dirigido… o de un falso positivo bloqueando a tus usuarios.
dataset
Cloudflare separa sus logs en conjuntos: http_requests (todas las peticiones), firewall_events (solo lo que tocó una regla), y otros. Cuál puedes leer depende del método, y eso condiciona todo lo demás.

Las tres vías, y cuál te corresponde

No hay una sola forma de sacar estos logs de Cloudflare, y la que elijas viene impuesta sobre todo por el plan que tengas contratado.

Antes de seguir · qué NO es tiempo real

Las vías A y B leen registros que Cloudflare consolida por lotes. El retraso es de minutos y no se puede reducir con configuración, por mucho que bajes el intervalo de sondeo: si pides datos más recientes que la ventana disponible, Cloudflare devuelve vacío.

Si necesitas ver un ataque mientras ocurre, la vía C es la única. Si te basta con mirar cinco minutos atrás —que para la mayoría de paneles es suficiente— A es mucho más simple de operar.

Vía A · El scrape config nativo de Promtail

Promtail trae soporte de Cloudflare de forma nativa: no hace falta ningún agente extra. Este bloque está verificado contra Promtail 2.9; su validador rechaza cualquier campo que no exista, así que estos son exactamente los que acepta.

promtail-config.ymlscrape de cloudflare
scrape_configs:
  - job_name: cloudflare_waf
    cloudflare:
      api_token: ${CF_API_TOKEN}     # token con permiso Logs:Read
      zone_id: ${CF_ZONE_ID}        # una zona = un dominio
      fields_type: extended       # default | minimal | extended | all
      pull_range: 5m              # cuánto pide en cada consulta
      workers: 3                  # descargas en paralelo
      labels:
        job: cloudflare_waf
        zone: midominio.com
        env: prod
CampoQué haceCuidado
api_tokenToken de Cloudflare con permiso Logs: Read sobre la zona.Token, no la Global API Key. Nunca en el archivo: por variable de entorno.
zone_idIdentifica el dominio. Está en el panel de Cloudflare, en Overview.Cambia por dominio y por entorno. Es el valor que más se equivoca al promocionar de staging a producción.
fields_typeCuántos campos trae cada registro.default no incluye los campos de WAF. Para ver acciones y reglas necesitas extended o all.
pull_rangeTamaño de la ventana que descarga en cada iteración.Muy corto y pides datos que Cloudflare aún no consolida: vendrán vacíos.
workersDescargas simultáneas.Subirlo acelera el arranque en zonas con mucho tráfico; también multiplica el consumo de memoria.
labelsEtiquetas fijas para todo lo que entre por aquí.Aquí es donde pones env y zone para poder separar entornos.
El detalle que confunde a todos

Este scrape config no tiene campo dataset. Lo comprobé: Promtail 2.9 rechaza dataset, account_id, endpoint y additional_fields como campos inexistentes. Solo acepta los seis de la tabla.

Eso significa que no lee firewall_events: lee http_requests, donde la información del WAF viene como campos dentro de cada petición (WAFAction, WAFRuleID, SecurityLevel…). Por eso fields_type importa tanto: con default esos campos sencillamente no vienen, y te quedas mirando un panel vacío sin entender por qué.

Vía C · Un Worker que empuja a Loki

Un Worker es código tuyo que Cloudflare ejecuta en su borde, en la misma petición. Como se ejecuta en el momento, puede mandar el evento a Loki al instante en vez de esperar a que se archive.

worker.jspush directo a Loki
export default {
  async fetch(request, env, ctx) {
    const response = await fetch(request);   // deja pasar la petición

    const cf = request.cf ?? {};
    const evento = {
      ClientIP:          request.headers.get("cf-connecting-ip"),
      ClientRequestURI:  new URL(request.url).pathname,
      ClientRequestMethod: request.method,
      ClientCountry:     cf.country ?? "xx",
      EdgeResponseStatus: response.status,
      WAFAction:         response.status === 403 ? "block" : "allow",
      RayID:             request.headers.get("cf-ray"),
    };

    // Las etiquetas van FUERA del texto: son el índice de Loki.
    const cuerpo = {
      streams: [{
        stream: {
          job:    "cloudflare_waf",
          zone:   env.ZONE,          // midominio.com
          env:    env.ENVIRONMENT,   // prod | staging
          action: evento.WAFAction,  // pocos valores: sirve como etiqueta
        },
        values: [[ `${Date.now()}000000`, JSON.stringify(evento) ]],
      }],
    };

    // waitUntil: el envío no retrasa la respuesta al visitante.
    ctx.waitUntil(
      fetch(env.LOKI_URL + "/loki/api/v1/push", {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          "Authorization": "Basic " + env.LOKI_AUTH,
        },
        body: JSON.stringify(cuerpo),
      }).catch(() => {})   // si Loki cae, la web sigue funcionando
    );

    return response;
  },
};
marca de tiempo
Loki la espera en nanosegundos. Date.now() da milisegundos, de ahí los seis ceros. Mandarla en milisegundos es el error más común: Loki interpreta la fecha en 1970 y la rechaza o la entierra.
ctx.waitUntil
Deja que el envío termine después de responder al visitante. Sin esto, cada petición de tu web espera a que Loki conteste.
.catch vacío
Deliberado. Si Loki no responde se pierde ese log, pero la web sigue sirviendo. Nunca dejes que tu sistema de observabilidad tire el servicio que observa.
action como etiqueta
Cabe porque tiene media docena de valores. ClientIP y RayID van dentro del JSON, jamás como etiquetas: son únicos por petición y te reventarían el índice (capítulo 04).
Esto obliga a exponer Loki a internet

El Worker corre en la red de Cloudflare, así que http://loki:3100 no existe para él. Necesita una URL pública, y eso cambia el problema: cualquiera que la descubra puede inyectar logs falsos o saturarte.

Como mínimo: HTTPS, autenticación (Basic Auth en un proxy delante de Loki, nunca Loki desnudo) y solo la ruta de push abierta —/loki/api/v1/push—, dejando las de consulta cerradas. Un túnel de Cloudflare hacia tu red es más limpio que abrir un puerto.

Consultar los eventos del WAF

Llegan como JSON, así que el parser es | json y cada campo queda disponible por su nombre. Estas consultas están probadas contra Loki con un evento real empujado por este mismo método.

Que el dashboard se actualice solo

De nada sirve ingerir rápido si el panel no se refresca. En Grafana, arriba a la derecha, se fija el intervalo de refresco; en el JSON del dashboard es el campo refresh.

dashboard.jsonrefresco y ventana
{
  "refresh": "10s",
  "time": { "from": "now-15m", "to": "now" }
}
Ajusta el refresco a la vía que uses

Con la vía C (Worker) un refresco de 10s tiene sentido: los datos llegan en segundos. Con las vías A o B, refrescar cada 10 s solo sirve para saturar a Loki con consultas que devuelven lo mismo, porque los datos nuevos tardan minutos. Ahí pon 1m y una ventana de now-1h.

Qué cambia entre entornos

Esta es la parte que rompe los despliegues. Nada de esto debería estar escrito a mano dentro de un archivo versionado.

El fallo que solo aparece el día del ataque

Un WAF en calma genera un goteo. Bajo un ataque genera picos de órdenes de magnitud más — y todos caen en el mismo stream, porque comparten etiquetas. El límite por stream (3 MB/s por defecto, capítulo 02) se agota y Loki empieza a descartar justo el tráfico que querías investigar.

Dimensiona per_stream_rate_limit pensando en tu pico, no en tu media. Y si separas por action, los bloqueos van a su propio stream y no compiten con el tráfico normal.

Qué está verificado en este capítulo y qué no

El esquema del scrape config de Cloudflare está comprobado contra Promtail 2.9: sus seis campos válidos y el rechazo de dataset, account_id, endpoint y additional_fields salen de ejecutar su validador. El envío por HTTP y las consultas LogQL están probados de extremo a extremo contra un Loki real.

Lo que no se probó aquí contra una cuenta real de Cloudflare es la descarga desde la Logpull API, que exige plan Enterprise. Los valores de latencia son los órdenes de magnitud documentados por Cloudflare, no medidas propias: contrástalos con tu zona antes de prometerle a nadie un panel “en vivo”.

Glosario

stream = combinación única de etiquetas chunk = bloque comprimido de un stream distributor = recibe y valida ingester = acumula en memoria querier = responde consultas cardinalidad = nº de streams distintos unwrap = campo de texto → número positions.yaml = memoria de Promtail provisioning = configurar Grafana por archivo tenant = inquilino aislado de Loki relabeling = derivar etiquetas de la ruta o del entorno WAF = cortafuegos de aplicación web zone = un dominio en Cloudflare Logpull / Logpush = leer o recibir logs de Cloudflare Worker = código tuyo en el borde de Cloudflare
Las cinco reglas

1. Pocas etiquetas, y de valores cerrados. Todo lo demás se extrae al consultar.
2. El selector primero y lo más estrecho posible; el parser después.
3. Antes de fiarte de un panel, mira cuántas series devuelve.
4. Los logs históricos van ordenados por fecha, o no entran.
5. Si Grafana no ve nada, revisa el rango de tiempo antes que la configuración.
